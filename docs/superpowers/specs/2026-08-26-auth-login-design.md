# Authentication (Login Gate) — Design Spec

**Date:** 2026-08-26
**Status:** Approved

---

## Overview

Adds authentication to `subscriptionManager` — today every `/api/**` endpoint is fully open (no
Spring Security dependency, confirmed nothing auth-related in `pom.xml`/`CorsConfig.java`) and the
frontend has no login screen. This closes the "Authentication / authorization" item in `CLAUDE.md`'s
"What's Not Built Yet" list.

**Explicitly scoped down**, based on discussion:
- **Login only, no roles/permissions.** A logged-in user can do everything the app already allows
  — the only gate is "authenticated or not." No `Role`/`Permission` model.
- **Session-cookie auth**, not JWT. Spring Security manages the session server-side; the browser
  sends the session cookie automatically (`credentials: 'include'`) — no token to store or attach
  by hand on the frontend.
- **Fixed, SQL-seeded users, no self-registration or user-management UI.** A couple of Ops
  accounts are inserted via a migration seed file, same pattern as `PLATFORM`/`PAYMENT_MODE`'s
  catalog seeding. No `POST /api/auth/register`, no admin screen to create users.
- **The entire app and every `/api/**` endpoint requires a session** — no endpoint stays public.

## Data Model

New table, following the `IDENTITY` catalog pattern (`PLATFORM`/`PAYMENT_MODE`), not the
sequence+trigger pattern used for transactional tables (`SUBSCRIPTIONS`/`RESOURCES`/`OPERATIONS`/
`SERVICE`) — `APP_USER` is a small, fixed, seeded set of accounts, not something the app creates
rows in at runtime:

```sql
CREATE TABLE SUBSCRIPTION_MANAGER.APP_USER (
    ID            NUMBER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    USERNAME      VARCHAR2(100) NOT NULL UNIQUE,
    PASSWORD_HASH VARCHAR2(200) NOT NULL
);
```

Migration `database/007-app-user.sql` (the next real schema file after `006-service.sql`; the two
most recent OpenSpec changes were docs-only and added no migration) creates the table and seeds
1-2 Ops accounts with a pre-computed BCrypt hash as a literal string (generated once, not computed
by the migration itself), matching `database/site/001-site.sql`'s seeding style for
`PLATFORM`/`PAYMENT_MODE`.

`USERNAME` avoids Oracle's reserved `USER` pseudo-column/keyword by using `APP_USER` as the table
name (not `USER`) — `USERNAME` as a column name has no such conflict.

## Backend

**New dependency:** `spring-boot-starter-security` in `pom.xml`.

**New entity/repository**, mirroring `Platform.java`/`PlatformRepository.java`'s `IDENTITY` pattern:
- `entity/AppUser.java` — `id` (`IDENTITY`), `username`, `passwordHash`.
- `repository/AppUserRepository.java` — `findByUsername(String username)`.

**`service/AppUserDetailsService.java`** — `implements UserDetailsService`, loads an `AppUser` by
username via the repository, throws `UsernameNotFoundException` if absent, wraps it in Spring
Security's `User` (username + password hash + no authorities, since there are no roles).

**`config/SecurityConfig.java`** replaces `config/CorsConfig.java` (CORS configuration moves here,
since it now needs `allowCredentials(true)` to let the session cookie travel cross-origin between
`localhost:3000` and `localhost:8080`):
- `SecurityFilterChain` bean: `/api/auth/login` permitted, every other `/api/**` request requires
  an authenticated session. CSRF disabled (this is a same-site JSON API consumed only by this
  app's own frontend, not a form-post surface — consistent with this being a session-cookie SPA
  pattern, not a traditional server-rendered form app).
- `PasswordEncoder` bean — `BCryptPasswordEncoder`.
- `AuthenticationManager` bean, backed by `AppUserDetailsService` + the `PasswordEncoder`.
- CORS: `allowedOrigins("http://localhost:3000")`, `allowCredentials(true)`, same methods as
  today's `CorsConfig`.

**`controller/AuthController.java`** (new `dto/LoginRequestDTO.java`: `username`/`password`):
- `POST /api/auth/login` — takes `LoginRequestDTO`, authenticates manually via
  `AuthenticationManager.authenticate(new UsernamePasswordAuthenticationToken(...))`, and on
  success stores the resulting `Authentication` into the `SecurityContext` and persists it to the
  HTTP session via Spring Security's `SecurityContextRepository` (`HttpSessionSecurityContextRepository`)
  — this is the standard "JSON login for an SPA" pattern, since Spring Security's default
  `formLogin()` expects form-urlencoded params and issues redirects, neither of which fits this
  app's all-JSON API. On authentication failure (`BadCredentialsException`), returns `401` with
  `Map.of("error", "Invalid username or password")`, matching `GlobalExceptionHandler`'s existing
  `Map<String, String>` error-body convention used everywhere else in this API.
- `POST /api/auth/logout` — invalidates the session (`HttpServletRequest.getSession().invalidate()`
  or Spring Security's `SecurityContextLogoutHandler`).
- `GET /api/auth/me` — returns the current authenticated username, or relies on the security
  filter chain itself to return `401` when there's no session (no need for the controller to check
  manually — an unauthenticated request never reaches this endpoint's body).

## Frontend

**`src/api.js`** (new): a single `apiFetch(path, options)` wrapping `fetch` with a fixed
`http://localhost:8080` base URL and `credentials: 'include'` on every call, so the session
cookie is always sent. On a `401` response, dispatches a `window` event (`auth:unauthorized`)
rather than redirecting directly — decouples "detecting an expired session" from "what the UI does
about it," which `App.jsx` owns.

**Every existing `fetch('http://localhost:8080/...')` call site** (across `App.jsx`,
`SubscriptionDetail.jsx`, `ClientsModule.jsx`, `AddClientForm.jsx`, `AddSubscriptionForm.jsx`,
`OperationsModule.jsx`, `DashboardModule.jsx`, and any others) moves to `apiFetch('/api/...')` —
mechanical, same HTTP method/headers/body/error-handling at each site, only the call itself
changes.

**`App.jsx`:**
- On mount, calls `apiFetch('/api/auth/me')`. Renders `LoadingState` while pending. A `401`
  response shows `LoginScreen` instead of the existing `AppShell` tree; a `200` shows the existing
  tree unchanged.
- Listens for the `auth:unauthorized` window event (from `api.js`) and resets to the "show login"
  state — covers a session expiring mid-use, not just the initial load.

**`components/LoginScreen.jsx`** (new): a minimal username/password form, `POST /api/auth/login`
via `apiFetch`, inline error on `401` (same inline-error-on-submit pattern already used by
`AddClientForm.jsx`/`SubscriptionDetail.jsx`'s action forms), success re-triggers `App.jsx`'s
auth check to switch to the authenticated tree.

**`components/shell/TopBar.jsx`**: gains a "Logout" button (today it only renders the brand/logo)
— `POST /api/auth/logout` via `apiFetch`, then the same reset-to-login path as `auth:unauthorized`.

## Testing

**Cross-cutting impact on existing tests:** 6 existing `@WebMvcTest` classes
(`CatalogControllerTest`, `ClientControllerTest`, `DashboardControllerTest`,
`ResourceControllerTest`, `SubscriptionControllerTest`, `SubscriptionLifecycleControllerTest`)
configure no security today. Once the `SecurityFilterChain` applies globally to `/api/**`, every
one of them starts failing (`401` instead of the expected `200`/`404`/etc.) unless updated. Each
gains `@WithMockUser` at the class level — simulates an authenticated request, verifying security
doesn't interfere with the legitimate flow those tests already cover, without those tests needing
to know anything about the auth mechanism itself.

**New tests:**
- `AuthControllerTest` — valid login → `200` + session established; invalid login → `401`;
  `/api/auth/me` without a session → `401`, with one → `200`; logout invalidates the session.
- `AppUserDetailsServiceTest` — loads by username; throws `UsernameNotFoundException` when absent.
- Frontend: `LoginScreen.test.js` (submit, inline error on invalid credentials); `App.test.js`
  gains cases for "no session → login screen" and "valid session → app tree"; a test confirming
  `apiFetch` sends `credentials: 'include'`.

## Risks

- **Migrating the 6 existing `@WebMvcTest` classes touches nearly every controller test file** —
  mechanical (one annotation each) but wide, high file-count/low-risk-per-file.
- **The seeded password hash is committed to the repo** (in the migration file, as a BCrypt hash,
  not plaintext). Accepted for a training/internal environment — a BCrypt hash isn't reversible,
  which is a meaningfully different risk profile than committing the Oracle DB password in
  cleartext (which this project already avoids via `.gitignore` on `application.properties`).

## Out of Scope

- Roles/permissions of any kind.
- Self-registration or a user-management UI/endpoint.
- "Remember me" / configurable session expiry — Spring Security's default session timeout applies.
- Login rate-limiting / brute-force protection.
